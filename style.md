## Wskazówki

### Wskaźniki do interfejsów

Praktycznie nigdy nie ma potrzeby używania wskaźników do interfejsów. Powinieneś przekazywać interfejs poprzez wartość – w dalszym ciągu możliwe jest, aby przekazywany obiekt był wskaźnikiem na dane.

Interfejs składa się z dwóch pól:

1. Wskaźnik na pewne informacje specyficzne dla typu. Możesz myśleć o tym jako o "typie".
2. Wskaźnik na dane. Jeśli przechowywaną wartością jest wskaźnik, jest on zapisywany bezpośrednio. W innym przypadku, gdy wartością są dane, przechowywany zostaje wskaźnik na te dane.

Jeśli więc chcesz, aby metody typu interfejsowego modyfikowały jego dane, musisz w nich używać wskaźnika.

### Weryfikuj zgodność z interfejsem

W razie potrzeby weryfikuj zgodność z interfejsem w czasie kompilacji. Np. dla:

- Wyeksportowanych typów, które są wymagane do wdrożenia określonych interfejsów w ramach kontraktu API
- Wyeksportowanych jak i nieeksportowanych typów będących częścią grupy typów implementujących ten sam interfejs
- Innych przypadków, w których naruszenie interfejsu spowodowałoby problemy po stronie użytkowników

<table>
<thead><tr><th>Źle</th><th>Dobrze</th></tr></thead>
<tbody>
<tr><td>

```go
type Handler struct {
  // ...
}



func (h *Handler) ServeHTTP(
  w http.ResponseWriter,
  r *http.Request,
) {
  ...
}
```

</td><td>

```go
type Handler struct {
  // ...
}

var _ http.Handler = (*Handler)(nil)

func (h *Handler) ServeHTTP(
  w http.ResponseWriter,
  r *http.Request,
) {
  // ...
}
```

</td></tr>
</tbody></table>

Instrukcja `var _ http.Handler = (*Handler)(nil)` spowoduje błąd kompilacji, jeżeli `*Handler` kiedykolwiek przestanie spełniać interfejs `http.Handler`.

Prawa strona przypisania powinna być wartością zerową testowanego (asserted) typu. Jest to `nil` dla wskaźników do typów (jak `*Handler`), wycinków oraz map, a także pusta struktura dla typów strukturalnych.

```go
type LogHandler struct {
  h   http.Handler
  log *zap.Logger
}

var _ http.Handler = LogHandler{}

func (h LogHandler) ServeHTTP(
  w http.ResponseWriter,
  r *http.Request,
) {
  // ...
}
```

### Odbiorniki (Receivers) i Interfejsy

Metody przynależące do wartości odbiornika mogą być wywoływane zarówno na jego wskaźnikach, jak i wartościach.
Metody przynależące do wskaźnika odbiornika (pointer receiver) mogą być wywoływane jedynie na jego wskaźnikach lub [wartościach adresowalnych](https://go.dev/ref/spec#Method_values).

Na przykład:

```go
type S struct {
  data string
}

func (s S) Read() string {
  return s.data
}

func (s *S) Write(str string) {
  s.data = str
}

// Nie możemy uzyskać wskaźników do wartości przechowywanych w mapach,
// ponieważ nie są one wartościami adresowalnymi.
sVals := map[int]S{1: {"A"}}

// Możemy wywołać Read na wartościach przechowywanych w mapie, ponieważ Read
// ma odbiornik wartościowy, który nie wymaga adresowalności.
sVals[1].Read()

// Nie możemy wywołać Write na wartościach przechowywanych w mapie, ponieważ Write
// ma odbiornik wskaźnikowy, a uzyskanie wskaźnika do elementu mapy jest niemożliwe.
//
//  sVals[1].Write("test")

sPtrs := map[int]*S{1: {"A"}}

// Możesz wywoływać zarówno Read, jak i Write, jeśli mapa przechowuje wskaźniki,
// ponieważ wskaźniki są z natury adresowalne.
sPtrs[1].Read()
sPtrs[1].Write("test")
```

Podobnie, interfejs może zostać spełniony poprzez wskaźnik, nawet jeśli odbiornikiem zadeklarowanej metody jest wartość, a nie wskaźnik.

```go
type F interface {
  f()
}

type S1 struct{}

func (s S1) f() {}

type S2 struct{}

func (s *S2) f() {}

s1Val := S1{}
s1Ptr := &S1{}
s2Val := S2{}
s2Ptr := &S2{}

var i F
i = s1Val
i = s1Ptr
i = s2Ptr

// Poniższy kod się nie skompiluje, ponieważ s2Val jest wartością, a brak odbiornika wartościowego dla f.
//   i = s2Val
```

Efektywny Go dobrze opisuje ten przypadek w rozdziale [Pointers vs. Values](https://go.dev/doc/effective_go#pointers_vs_values).

### Kopiuj wycinki i mapy w punktach stycznych kodu

Ze względu na to, że wycinki i mapy zawierają wskaźniki (pointers) na przechowywane pod spodem dane,

#### Odbieranie wycinków i map

#### Zwracanie wycinków i map

Podobnie jak w poprzednim przypadku, uważaj na sytuacje, w których modyfikacja zwróconych map lub wycinków mogłaby ujawnić i naruszyć wewnętrzny stan struktury

<table>
<thead><tr><th>Źle</th><th>Dobrze</th></tr></thead>
<tbody>
<tr><td>

```go
type Stats struct {
  mu sync.Mutex
  counters map[string]int
}

// Snapshot zwraca aktualne statystyki.
func (s *Stats) Snapshot() map[string]int {
  s.mu.Lock()
  defer s.mu.Unlock()

  return s.counters
}

// snapshot nie jest już chroniony przez mutex,
// więc dowolna próba dostępu narażona jest na wyścig (data race).
snapshot := stats.Snapshot()
```

</td><td>

```go
type Stats struct {
  mu sync.Mutex
  counters map[string]int
}

func (s *Stats) Snapshot() map[string]int {
  s.mu.Lock()
  defer s.mu.Unlock()

  result := make(map[string]int, len(s.counters))
  for k, v := range s.counters {
    result[k] = v
  }
  return result
}

// Snapshot jest teraz kopią.
snapshot := stats.Snapshot()
```

</td></tr>
</tbody></table>

### Stosuj "defer" do operacji czyszczących (clean-up)

Używaj instrukcji `defer` do czyszczenia zasobów, takich jak pliki czy blokady (locks).

<table>
<thead><tr><th>Źle</th><th>Dobrze</th></tr></thead>
<tbody>
<tr><td>

```go
p.Lock()
if p.count < 10 {
  p.Unlock()
  return p.count
}

p.count++
newCount := p.count
p.Unlock()

return newCount

// Łatwo o pominięcie odblokowania ze względu na wiele instrukcji "return".
```

</td><td>

```go
p.Lock()
defer p.Unlock()

if p.count < 10 {
  return p.count
}

p.count++
return p.count

// Bardziej czytelne.
```

</td></tr>
</tbody></table>

Instrukcja `defer` ma niezwykle mały narzut i należy jej unikać jedynie wtedy, gdy można udowodnić, że czas wykonania funkcji jest rzędu nanosekund. Korzyści w czytelności kodu wynikające z jej stosowania są warte minimalnego kosztu wywołania. Powyższe stwierdzenie jest szczególnie prawdziwe dla większych metod robiących więcej niż tylko proste operacje na pamięci, w przypadku których inne operacje mają większe znaczenie niż `defer`.

### Kanały (channels) powinny mieć rozmiar 1 lub być niebuforowane

Zazwyczaj kanały powinny mieć rozmiar 1 lub być niebuforowane.
Domyślnie kanały są niebuforowane i mają rozmiar 0.
Każdy inny rozmiar musi podlegać ścisłej kontroli.
Zastanów się co wpływa na rozmiar kanału, co zapobiegnie jego zapełnianiu się pod wpływem obciążenia
i blokowaniu zapisu oraz co się stanie gdy taki scenariusz wystąpi.


</td><td>

```go
// Rozmiar równy 1
```

### Rozpoczynaj wyliczenia od 1

Standardowym sposobem wprowadzania wyliczeń (enums) w Go jest zadeklarowanie własnego typu oraz zgrupowanie `const` z użyciem `iota`. Ponieważ wartością domyślną zmiennych jest 0, dobrą praktyką jest rozpoczynanie wyliczania od wartości niezerowej.

<table>
<thead><tr><th>Źle</th><th>Dobrze</th></tr></thead>
<tbody>
<tr><td>

```go
type Operation int

const (
  Add Operation = iota
  Subtract
  Multiply
)

// Add=0, Subtract=1, Multiply=2
```

</td><td>

```go
type Operation int

const (
  Add Operation = iota + 1
  Subtract
  Multiply
)

// Add=1, Subtract=2, Multiply=3
```

</td></tr>
</tbody></table>

Są przypadki, w których użycie wartości zerowej ma sens, na przykład gdy wartość zerowa opisuje pożądane zachowanie domyślne.

```go
type LogOutput int

const (
  LogToStdout LogOutput = iota
  LogToFile
  LogToRemote
)

// LogToStdout=0, LogToFile=1, LogToRemote=2
```

### Używaj pakietu `"time"` do obsługi czasu

Czas to skomplikowany temat. Nieprawidłowe założenia często dotyczące czasu zakładają, że:

1. Dzień ma 24 godziny
2. Godzina składa się z 60 minut
3. Tydzień ma 7 dni
4. Rok to 365 dni
5. [Oraz wiele innych](https://infiniteundo.com/post/25326999628/falsehoods-programmers-believe-about-time)

Dla przykładu przypadek *1* oznacza, że dodanie 24 godzin do pewnego punktu w czasie nie zawsze zagwarantuje otrzymanie kolejnego dnia kalendarzowego.

Dlatego zawsze używaj pakietu [`"time"`](https://pkg.go.dev/time), gdy masz do czynienia z czasem, ponieważ pomaga on radzić sobie z błędnymi założeniami w bezpieczniejszy i dokładniejszy sposób.

#### Używaj `time.Time` dla punktów w czasie

Użyj [`time.Time`](https://pkg.go.dev/time#Time), gdy pracujesz z punktami w czasie, oraz metod na `time.Time` przy porównywaniu, dodawaniu lub odejmowaniu czasu.

<table>
<thead><tr><th>Źle</th><th>Dobrze</th></tr></thead>
<tbody>
<tr><td>

```go
func isActive(now, start, stop int) bool {
  return start <= now && now < stop
}
```

</td><td>

```go
func isActive(now, start, stop time.Time) bool {
  return (start.Before(now) || start.Equal(now)) && now.Before(stop)
}
```

</td></tr>
</tbody></table>

#### Używaj `time.Duration` dla przedziałów czasowych

Używaj [`time.Duration`](https://pkg.go.dev/time#Duration) do obsługi przedziałów czasowych.

<table>
<thead><tr><th>Źle</th><th>Dobrze</th></tr></thead>
<tbody>
<tr><td>

```go
func poll(delay int) {
  for {
    // ...
    time.Sleep(time.Duration(delay) * time.Millisecond)
  }
}

poll(10) // czy to były sekundy czy milisekundy?
```

</td><td>

```go
  for {
    // ...
    time.Sleep(delay)
  }
}

poll(10*time.Second)
```

</td></tr>
</tbody></table>

Wracając do przykładu z dodawaniem 24 godzin do punktu w czasie, użyta metoda zależy od intencji. Jeżeli chcemy uzyskać tę samą porę dnia, lecz następnego dnia kalendarzowego, powinniśmy użyć [`Time.AddDate`](https://pkg.go.dev/time#Time.AddDate). Jednakże, jeżeli chcemy gwarancji punktu w czasie przesuniętego dokładnie o 24 godziny, należy użyć [`Time.Add`](https://pkg.go.dev/time#Time.Add).

```go
newDay := t.AddDate(0 /* lata */, 0 /* miesiące */, 1 /* dni */)
maybeNewDay := t.Add(24 * time.Hour)
```

#### Używaj `time.Time` oraz `time.Duration` z systemami zewnętrznymi

Używaj `time.Duration` i `time.Time` w interakcjach z systemami zewnętrznymi, gdy tylko to możliwe. Na przykład:

- Flagi linii poleceń: pakiet [`flag`](https://pkg.go.dev/flag) wspiera `time.Duration` poprzez [`time.ParseDuration`](https://pkg.go.dev/time#ParseDuration)
- JSON: [`encoding/json`](https://pkg.go.dev/encoding/json) wspiera kodowanie `time.Time` jako ciąg znaków zgodny z [RFC 3339](https://tools.ietf.org/html/rfc3339) poprzez [metodę `UnmarshalJSON`]
- SQL: [`database/sql`](https://pkg.go.dev/database/sql) wspiera konwersję z kolumn `DATETIME` oraz `TIMESTAMP` na `time.Time` i z powrotem, jeśli sterownik to obsługuje
- YAML: [`gopkg.in/yaml.v2`](https://pkg.go.dev/gopkg.in/yaml.v2) wspiera `time.Time` jako ciąg zgodny z [RFC 3339](https://tools.ietf.org/html/rfc3339) oraz `time.Duration` poprzez [`time.ParseDuration`](https://pkg.go.dev/time#ParseDuration).

Gdy nie jest możliwe użycie `time.Duration` w tych interakcjach, użyj `int` lub `float64` i dołącz jednostkę do nazwy pola.

Na przykład, ponieważ `encoding/json` nie obsługuje `time.Duration`, nazwa jednostki została zawarta w nazwie pola.

<table>
<thead><tr><th>Źle</th><th>Dobrze</th></tr></thead>
<tbody>
<tr><td>

```go
// {"interval": 2}
type Config struct {
  Interval int `json:"interval"`
}
```

</td><td>

```go
// {"intervalMillis": 2000}
type Config struct {
  IntervalMillis int `json:"intervalMillis"`
}
```

</td></tr>
</tbody></table>

Gdy nie jest możliwe użycie `time.Time` w tych interakcjach, chyba że uzgodniono inaczej, użyj typu `string` i formatuj znaczniki czasu (timestamps) zgodnie z definicją w [RFC 3339](https://tools.ietf.org/html/rfc3339). Format ten jest stosowany domyślnie przez [`Time.UnmarshalText`](https://pkg.go.dev/time#Time.UnmarshalText) i jest dostępny w `Time.Format` oraz `time.Parse` poprzez [`time.RFC3339`](https://pkg.go.dev/time#RFC3339).

Choć w praktyce rzadko stanowi to problem, pamiętaj, że pakiet `"time"` nie obsługuje parsowania znaczników czasu z sekundami przestępnymi ([8728](https://github.com/golang/go/issues/8728)), ani nie uwzględnia ich w obliczeniach ([15190](https://github.com/golang/go/issues/15190)). Jeśli porównasz dwa punkty w czasie, różnica nie obejmie sekund przestępnych, które mogły w tym czasie wystąpić.

### Błędy

#### Typy błędów

Istnieje kilka opcji deklarowania błędów. Rozważ poniższe kwestie przed wyborem optymalnego rozwiązania:

- Czy kod wywołujący musi dopasować błąd, aby móc go obsłużyć?
  Jeśli tak, musimy zapewnić obsługę funkcji [`errors.Is`](https://pkg.go.dev/errors#Is) lub [`errors.As`](https://pkg.go.dev/errors#As) poprzez zadeklarowanie zmiennej błędu najwyższego poziomu lub własnego typu.
- Czy komunikat błędu jest statycznym ciągiem znaków, czy dynamicznym, wymagającym informacji kontekstowych?
  W pierwszym przypadku użyjemy [`errors.New`](https://pkg.go.dev/errors#New), w drugim – [`fmt.Errorf`](https://pkg.go.dev/fmt#Errorf) lub własnego typu błędu.
- Czy propagujemy nowy błąd zwrócony przez funkcję niższego poziomu?
  Jeśli tak, zobacz [sekcję o opakowywaniu błędów](#opakowywanie-b%C5%82%C4%99d%C3%B3w-error-wrapping).

| Dopasowanie błędu? | Komunikat błędu | Wytyczne                                                                  |
|--------------------|-----------------|---------------------------------------------------------------------------|
| Nie                | statyczny       | [`errors.New`](https://pkg.go.dev/errors#New)                             |
| Nie                | dynamiczny      | [`fmt.Errorf`](https://pkg.go.dev/fmt#Errorf)                             |
| Tak                | statyczny       | `var` najwyższego poziomu z [`errors.New`](https://pkg.go.dev/errors#New) |
| Tak                | dynamiczny      | własny typ `error`                                                        |

Na przykład, użyj [`errors.New`](https://pkg.go.dev/errors#New) dla błędu ze statycznym komunikatem. Wyeksportuj ten błąd jako zmienną, aby umożliwić jego dopasowanie za pomocą `errors.Is`, jeśli kod wywołujący tego wymaga.

<table>
<thead><tr><th>Brak dopasowywania błędów</th><th>Dopasowywanie błędów</th></tr></thead>
<tbody>
<tr><td>

```go
// pakiet foo

func Open() error {
  return errors.New("could not open")
}

// pakiet bar

if err := foo.Open(); err != nil {
  // Nie można obsłużyć błędu.
  panic("unknown error")
}
```

</td><td>

```go
// pakiet foo

var ErrCouldNotOpen = errors.New("could not open")

func Open() error {
  return ErrCouldNotOpen
}

// pakiet bar

if err := foo.Open(); err != nil {
  if errors.Is(err, foo.ErrCouldNotOpen) {
    // obsługa błędu
  } else {
    panic("unknown error")
  }
}
```

</td></tr>
</tbody></table>

W przypadku błędu z dynamicznym ciągiem znaków użyj [`fmt.Errorf`](https://pkg.go.dev/fmt#Errorf), jeśli kod wywołujący nie musi go dopasowywać, lub własnego typu `error`, gdy takie dopasowanie jest konieczne.

<table>
<thead><tr><th>Brak dopasowywania błędów</th><th>Dopasowywanie błędów</th></tr></thead>
<tbody>
<tr><td>

```go
// pakiet foo

func Open(file string) error {
  return fmt.Errorf("file %q not found", file)
}

// pakiet bar

if err := foo.Open("testfile.txt"); err != nil {
  // Nie można obsłużyć błędu.
  panic("unknown error")
}
```

</td><td>

```go
// pakiet foo

type NotFoundError struct {
  File string
}

func (e *NotFoundError) Error() string {
  return fmt.Sprintf("file %q not found", e.File)
}

func Open(file string) error {
  return &NotFoundError{File: file}
}


// pakiet bar

if err := foo.Open("testfile.txt"); err != nil {
  var notFound *NotFoundError
  if errors.As(err, &notFound) {
    // obsługa błędu
  } else {
    panic("unknown error")
  }
}
```

</td></tr>
</tbody></table>

Pamiętaj, że eksportując zmienne lub typy błędów z pakietu, czynisz je częścią jego publicznego API.

#### Opakowywanie błędów (Error Wrapping)

Istnieją trzy główne sposoby propagacji błędów w przypadku błędu wywołania funkcji:

- Zwróć oryginalny błąd w niezmienionej postaci.
- Dodaj kontekst za pomocą `fmt.Errorf` i czasownika `%w`.
- Dodaj kontekst za pomocą `fmt.Errorf` i czasownika `%v`.

Zwróć oryginalny błąd bez zmian, jeśli nie ma potrzeby dodawania dodatkowego kontekstu. Zachowuje to oryginalny typ i komunikat błędu. Jest to odpowiednie rozwiązanie, gdy komunikat błędu bazowego zawiera wystarczające informacje do zidentyfikowania jego źródła.

W przeciwnym razie dodawaj kontekst do komunikatu błędu tam, gdzie to możliwe, aby zamiast ogólnego "connection refused" otrzymać przydatny komunikat, np. "call service foo: connection refused".

Stosuj `fmt.Errorf` do dodawania kontekstu, wybierając między czasownikami `%w` a `%v` na podstawie tego, czy kod wywołujący powinien mieć możliwość dopasowania i wyekstrahowania przyczyny źródłowej:

- Użyj `%w`, jeśli kod wywołujący powinien mieć dostęp do błędu bazowego. Jest to dobry domyślny wybór dla większości opakowywanych błędów, jednak pamiętaj, że wywołujący mogą zacząć polegać na tym zachowaniu. Jeśli więc opakowywany błąd jest znaną zmienną (`var`) lub typem, udokumentuj go i przetestuj jako część kontraktu funkcji.
- Użyj `%v`, aby zaciemnić błąd bazowy. Kod wywołujący nie będzie mógł go dopasować, ale w przyszłości będziesz mógł zmienić czasownik na `%w`, jeśli zajdzie taka potrzeba.

Dodając kontekst do zwracanych błędów, dbaj o jego zwięzłość i unikaj zwrotów takich jak "failed to", które opisują rzeczy oczywiste i kumulują się na kolejnych poziomach stosu wywołań:

<table>
<thead><tr><th>Źle</th><th>Dobrze</th></tr></thead>
<tbody>
<tr><td>

```go
s, err := store.New()
if err != nil {
    return fmt.Errorf(
        "failed to create new store: %w", err)
}
```

</td><td>

```go
s, err := store.New()
if err != nil {
    return fmt.Errorf(
        "new store: %w", err)
}
```

</td></tr><tr><td>

```plain
failed to x: failed to y: failed to create new store: the error
```

</td><td>

```plain
x: y: new store: the error
```

</td></tr>
</tbody></table>

Jednakże, gdy błąd ma trafić do innego systemu, wiadomość powinna jednoznacznie wskazywać na błąd (np. poprzez tag `err` lub prefiks "Failed" w logach).

Zobacz również [Don't just check errors, handle them gracefully](https://dave.cheney.net/2016/04/27/dont-just-check-errors-handle-them-gracefully).

#### Nazewnictwo błędów

Dla wartości błędów przechowywanych jako zmienne globalne stosuj prefiks `Err` lub `err` w zależności od tego, czy są eksportowane. Ta zasada zastępuje wytyczną [Rozpoczynaj nieeksportowane zmienne globalne znakiem _](#rozpoczynaj-nieeksportowane-zmienne-globalne-znakiem-_).

```go
var (
  // Poniższe dwa błędy są eksportowane,
  // aby użytkownicy pakietu mogli je dopasować za pomocą errors.Is.

  ErrBrokenLink = errors.New("link is broken")
  ErrCouldNotOpen = errors.New("could not open")

  // Ten błąd nie jest eksportowany, ponieważ
  // nie chcemy czynić go częścią publicznego API.
  // Nadal możemy go używać wewnątrz pakietu z errors.Is.

  errNotFound = errors.New("not found")
)
```

W przypadku własnych typów błędów używaj przyrostka `Error`.

```go
// Podobnie, ten błąd jest eksportowany,
// aby użytkownicy pakietu mogli go dopasować za pomocą errors.As.

type NotFoundError struct {
  File string
}

func (e *NotFoundError) Error() string {
  return fmt.Sprintf("file %q not found", e.File)
}

// Ten błąd nie jest eksportowany, ponieważ
// nie chcemy czynić go częścią publicznego API.
// Nadal możemy z niego korzystać wewnątrz pakietu z errors.As.

type resolveError struct {
  Path string
}

func (e *resolveError) Error() string {
  return fmt.Sprintf("resolve %q", e.Path)
}
```

#### Obsługuj błędy tylko raz

Gdy kod wywołujący otrzyma błąd od wywoływanego, może go obsłużyć na różne sposoby w zależności od posiadanych informacji.

Opcje te obejmują między innymi:

- dopasowanie błędu za pomocą `errors.Is` lub `errors.As` i odpowiednią obsługę odgałęzień (jeśli kontrakt wywoływanego definiuje konkretne błędy)
- zalogowanie błędu i łagodne przejście w stan obniżonej wydajności/funkcjonalności (degrade gracefully), jeśli błąd jest odzyskiwalny
- zwrócenie dobrze zdefiniowanego błędu domenowego, jeśli problem dotyczy specyficznego stanu domeny
- zwrócenie błędu w formie [opakowanej](#opakowywanie-b%C5%82%C4%99d%C3%B3w-error-wrapping) lub dosłownej

Niezależnie od sposobu obsługi, błąd powinien być zazwyczaj obsługiwany **tylko raz**. Kod wywołujący nie powinien np. logować błędu, a następnie go zwracać, ponieważ jego własny kod wywołujący również może ten błąd obsłużyć.

Rozważ poniższe przypadki:

<table>
<thead><tr><th>Opis</th><th>Kod</th></tr></thead>
<tbody>
<tr><td>

**Źle**: Zaloguj błąd i go zwróć

Kod wywołujący w dalszej części stosu z dużym prawdopodobieństwem podejmie podobne działanie. Generuje to duży hałas w logach przy znikomej wartości.

</td><td>

```go
u, err := getUser(id)
if err != nil {
  // ŹLE: Zobacz opis
  log.Printf("Could not get user %q: %v", id, err)
  return err
}
```

</td></tr>
<tr><td>

**Dobrze**: Opakuj błąd i go zwróć

Wyższe warstwy stosu wywołań obsłużą błąd. Użycie `%w` daje pewność, że będą mogły dopasować błąd za pomocą `errors.Is` lub `errors.As`.

</td><td>

```go
u, err := getUser(id)
if err != nil {
  return fmt.Errorf("get user %q: %w", id, err)
}
```

</td></tr>
<tr><td>

**Dobrze**: Zaloguj błąd i przejdź w stan obniżonej funkcjonalności

Jeśli operacja nie jest bezwzględnie konieczna, możemy zapewnić działanie aplikacji w trybie obniżonej funkcjonalności poprzez podjęcie próby naprawczej.

</td><td>

```go
if err := emitMetrics(); err != nil {
  // Niepowodzenie zapisu metryk nie powinno
  // przerywać działania aplikacji.
  log.Printf("Could not emit metrics: %v", err)
}

```

</td></tr>
<tr><td>

**Dobrze**: Dopasuj błąd i przejdź w stan obniżonej funkcjonalności

Jeśli wywoływany kod definiuje konkretny błąd w swoim kontrakcie, a błąd jest odzyskiwalny, dopasuj ten przypadek i obsłuż go łagodnie. Dla pozostałych przypadków opakuj błąd i zwróć go.

Wyższe warstwy stosu obsłużą pozostałe błędy.

</td><td>

```go
tz, err := getUserTimeZone(id)
if err != nil {
  if errors.Is(err, ErrUserNotFound) {
    // Użytkownik nie istnieje. Użyj UTC.
    tz = time.UTC
  } else {
    return fmt.Errorf("get user %q: %w", id, err)
  }
}
```

</td></tr>
</tbody></table>

### Nie "panikuj"

Kod działający produkcyjnie musi unikać paniki. Instrukcje `panic` są głównym źródłem tzw. [awarii kaskadowych](https://en.wikipedia.org/wiki/Cascading_failure). Jeśli błąd wystąpi, funkcja musi go zwrócić i umożliwić wywołującemu podjęcie decyzji o sposobie obsługi.

<table>
<thead><tr><th>Źle</th><th>Dobrze</th></tr></thead>
<tbody>
<tr><td>

```go
func run(args []string) {
  if len(args) == 0 {
    panic("an argument is required")
  }
  // ...
}

func main() {
  run(os.Args[1:])
}
```

</td><td>

```go
func run(args []string) error {
  if len(args) == 0 {
    return errors.New("an argument is required")
  }
  // ...
  return nil
}

func main() {
  if err := run(os.Args[1:]); err != nil {
    fmt.Fprintln(os.Stderr, err)
    os.Exit(1)
  }
}
```

</td></tr>
</tbody></table>

Konstrukcja panic/recover nie stanowi strategii obsługi błędów. Program powinien panikować dopiero wtedy, gdy wystąpi sytuacja nieodzyskiwalna, taka jak dereferencja wskaźnika nil. Wyjątek stanowi etap inicjalizacji: błędy podczas uruchamiania programu, które powinny przerwać jego działanie, mogą wywołać panikę.

```go
var _statusTemplate = template.Must(template.New("name").Parse("_statusHTML"))
```

Nawet w testach preferuj `t.Fatal` lub `t.FailNow` zamiast paniki, aby upewnić się, że test zostanie wyraźnie oznaczony jako nieudany.

<table>
<thead><tr><th>Źle</th><th>Dobrze</th></tr></thead>
<tbody>
<tr><td>

```go
// func TestFoo(t *testing.T)

f, err := os.CreateTemp("", "test")
if err != nil {
  panic("failed to set up test")
}
```

</td><td>

```go
// func TestFoo(t *testing.T)

f, err := os.CreateTemp("", "test")
if err != nil {
  t.Fatal("failed to set up test")
}
```

</td></tr>
</tbody></table>

### Używaj go.uber.org/atomic

Operacje atomowe z pakietu [sync/atomic](https://pkg.go.dev/sync/atomic) operują na surowych typach danych (`int32`, `int64` itp.), przez co łatwo zapomnieć o użyciu operacji atomowej do odczytu lub modyfikacji zmiennej.

Biblioteka [go.uber.org/atomic](https://pkg.go.dev/go.uber.org/atomic) zwiększa bezpieczeństwo typów poprzez ukrycie typu bazowego. Dodatkowo zawiera wygodny typ `atomic.Bool`.

<table>
<thead><tr><th>Źle</th><th>Dobrze</th></tr></thead>
<tbody>
<tr><td>

```go
type foo struct {
  running int32  // atomic
}

func (f *foo) start() {
  if atomic.SwapInt32(&f.running, 1) == 1 {
     // już działa…
     return
  }
  // uruchom Foo
}

func (f *foo) isRunning() bool {
  return f.running == 1  // wyścig (race)!
}
```

</td><td>

```go
type foo struct {
  running atomic.Bool
}

func (f *foo) start() {
  if f.running.Swap(true) {
     // już działa…
     return
  }
  // uruchom Foo
}

func (f *foo) isRunning() bool {
  return f.running.Load()
}
```

</td></tr>
</tbody></table>

### Unikaj mutowalnych zmiennych globalnych

Unikaj modyfikowania zmiennych globalnych – zamiast tego stosuj wstrzykiwanie zależności (dependency injection). Dotyczy to zarówno wskaźników do funkcji, jak i innych wartości.

<table>
<thead><tr><th>Źle</th><th>Dobrze</th></tr></thead>
<tbody>
<tr><td>

```go
// sign.go

var _timeNow = time.Now

func sign(msg string) string {
  now := _timeNow()
  return signWithTime(msg, now)
}
```

</td><td>

```go
// sign.go

type signer struct {
  now func() time.Time
}
```

### Unikaj osadzania typów (type embedding) w strukturach publicznych

Typy osadzane w strukturach publicznych ujawniają szczegóły implementacji, ograniczają ewolucję typów oraz zaciemniają dokumentację.

Zakładając, że zaimplementowałeś różne typy list przy użyciu współdzielonego `AbstractList`, unikaj osadzania `AbstractList` w konkretnych implementacjach list. Zamiast tego jawnie zaimplementuj w swojej strukturze metody delegowujące wykonanie do abstrakcyjnego typu.

```go
type AbstractList struct {}

// Add dodaje element do listy.
func (l *AbstractList) Add(e Entity) {
  // ...
}

// Remove usuwa element z listy.
func (l *AbstractList) Remove(e Entity) {
  // ...
}
```

<table>
<thead><tr><th>Źle</th><th>Dobrze</th></tr></thead>
<tbody>
<tr><td>

```go
// ConcreteList stanowi listę elementów.
type ConcreteList struct {
  *AbstractList
}
```

</td><td>

```go
// ConcreteList stanowi listę elementów.
type ConcreteList struct {
  list *AbstractList
}

// Add dodaje element do listy.
func (l *ConcreteList) Add(e Entity) {
  l.list.Add(e)
}

// Remove usuwa element z listy.
func (l *ConcreteList) Remove(e Entity) {
  l.list.Remove(e)
}
```

</td></tr>
</tbody></table>

Go pozwala na [osadzanie typów (type embedding)](https://go.dev/doc/effective_go#embedding) jako kompromis między dziedziczeniem a kompozycją. Typ zewnętrzny otrzymuje niejawne kopie metod typu osadzonego. Metody te domyślnie delegują zadanie do osadzonej instancji.

W procesie osadzania struktura zyskuje pole o tej samej nazwie co osadzony typ. Zatem jeśli typ osadzony jest publiczny, pole również staje się publiczne. W celu zachowania kompatybilności wstecznej każda przyszła wersja typu zewnętrznego będzie musiała zachować ten osadzony typ.

Osadzanie typów jest rzadko potrzebne. To ułatwienie pozwalające uniknąć żmudnego pisania metod delegujących.

Nawet osadzenie kompatybilnego *interfejsu* `AbstractList` zamiast struktury dałoby deweloperowi większą elastyczność na przyszłość, jednak nadal ujawniałoby informację, że konkretne listy korzystają z abstrakcyjnej implementacji.

<table>
<thead><tr><th>Źle</th><th>Dobrze</th></tr></thead>
<tbody>
<tr><td>

```go
// AbstractList stanowi ogólną implementację
// dla kilku typów list elementów.
type AbstractList interface {
  Add(Entity)
  Remove(Entity)
}

// ConcreteList stanowi listę elementów.
type ConcreteList struct {
  AbstractList
}
```

</td><td>

```go
// ConcreteList stanowi listę elementów.
type ConcreteList struct {
  list AbstractList
}

// Add dodaje element do listy.
func (l *ConcreteList) Add(e Entity) {
  l.list.Add(e)
}

// Remove usuwa element z listy.
func (l *ConcreteList) Remove(e Entity) {
  l.list.Remove(e)
}
```

</td></tr>
</tbody></table>

Zarówno w przypadku osadzania struktur, jak i interfejsów, osadzany typ nakłada ograniczenia na ewolucję typu zewnętrznego.

- Dodawanie metod do osadzonego interfejsu to zmiana łamiąca kompatybilność (breaking change).
- Usuwanie metod z osadzonej struktury to zmiana łamiąca kompatybilność.
- Usuwanie typu osadzonego to zmiana łamiąca kompatybilność.
- Zastąpienie typu osadzonego (nawet zamiennikiem spełniającym ten sam interfejs) to zmiana łamiąca kompatybilność.

Choć pisanie metod delegujących bywa uciążliwe, dodatkowy wysiłek ukrywa szczegóły implementacji, pozostawia przestrzeń na zmiany i eliminuje pośrednictwo przy zapoznawaniu się z pełnym interfejsem w dokumentacji.

### Unikaj używania nazw elementów wbudowanych (built-in names)

[Specyfikacja języka Go](https://go.dev/ref/spec) określa zestaw wbudowanych,

W zależności od kontekstu ponowne użycie tych identyfikatorów przesłoni (shadow)

że kod zacznie wprowadzać w błąd. W najlepszym przypadku kompilator zgłosi błąd;
w najgorszym kod wprowadzi ukryte, trudne do wykrycia błędy.

### Unikaj `init()`

Unikaj funkcji `init()` tam, gdzie to możliwe. Gdy użycie `init()` jest nieuniknione lub wysoce pożądane, kod powinien:

1. Być całkowicie deterministyczny i niezależny od środowiska czy sposobu wywołania programu.
2. Unikać zależności od kolejności lub efektów ubocznych (side-effects) innych funkcji `init()`. Podczas gdy kolejność wywoływania `init()` jest dobrze znana, kod może się zmieniać, a relacje między funkcjami `init()` mogą uczynić go podatnym na błędy.
3. Unikać dostępu lub modyfikacji stanu globalnego i środowiskowego (takich jak informacje o maszynie, zmienne środowiskowe, katalog roboczy, argumenty wejściowe programu itp.).
4. Unikać operacji wejścia/wyjścia (I/O), w tym operacji na systemie plików, sieci oraz wywołań systemowych.

Kod, który nie spełnia tych wymagań, prawdopodobnie powinien być funkcją pomocniczą wywoływaną w ramach `main()` (lub w innym momencie cyklu życia programu) bądź stanowić część samej funkcji `main()`. W szczególności biblioteki tworzone z myślą o użyciu przez inne programy powinny zachować szczególną ostrożność, aby być w pełni deterministyczne i nie wykonywać "magii podczas inicjalizacji".

<table>
<thead><tr><th>Źle</th><th>Dobrze</th></tr></thead>
<tbody>
<tr><td>

```go
type Foo struct {
    // ...
}

var _defaultFoo Foo

func init() {
    _defaultFoo = Foo{
        // ...
    }
}
```

</td><td>

```go
var _defaultFoo = Foo{
    // ...
}

// lub lepiej, dla testowalności:

var _defaultFoo = defaultFoo()

func defaultFoo() Foo {
    return Foo{
        // ...
    }
}
```

</td></tr>
<tr><td>

```go
type Config struct {
    // ...
}

var _config Config

func init() {
    // Źle: bazuje na bieżącym katalogu
    cwd, _ := os.Getwd()

    // Źle: operacje wejścia/wyjścia (I/O)
    raw, _ := os.ReadFile(
        path.Join(cwd, "config", "config.yaml"),
    )

    yaml.Unmarshal(raw, &_config)
}
```

</td><td>

```go
type Config struct {
    // ...
}

func loadConfig() Config {
    cwd, err := os.Getwd()
    // obsługa err

    raw, err := os.ReadFile(
        path.Join(cwd, "config", "config.yaml"),

    // obsługa err

    yaml.Unmarshal(raw, &config)

}
```

</tbody></table>

Biorąc pod uwagę powyższe, niektóre sytuacje, w których `init()` może być preferowane lub niezbędne, obejmują:

- Złożone wyrażenia, których nie można przedstawić jako pojedynczych przypisań.
- Wtyczki (pluggable hooks), takie jak dialekty `database/sql`, rejestry typów kodowania itp.
- Optymalizacje pod kątem [Google Cloud Functions](https://cloud.google.com/functions/docs/bestpractices/tips#use_global_variables_to_reuse_objects_in_future_invocations) i innych form deterministycznych obliczeń wstępnych.

### Zakończenie działania programu w `main()`

Programy w Go używają [`os.Exit`](https://pkg.go.dev/os#Exit) lub [`log.Fatal*`](https://pkg.go.dev/log#Fatal) do natychmiastowego zakończenia pracy. (Wywoływanie paniki nie jest właściwym sposobem na zamykanie programu – zobacz [Nie "panikuj"](#nie-panikuj).)

Wywołuj `os.Exit` lub `log.Fatal*` **wyłącznie w funkcji `main()`**. Wszystkie inne funkcje powinny zwracać błędy, aby zasygnalizować niepowodzenie.

<table>
<thead><tr><th>Źle</th><th>Dobrze</th></tr></thead>
<tbody>
<tr><td>

```go
func main() {
  body := readFile(path)
  fmt.Println(body)
}

func readFile(path string) string {
  f, err := os.Open(path)
  if err != nil {
    log.Fatal(err)
  }

  b, err := io.ReadAll(f)
  if err != nil {
    log.Fatal(err)
  }

  return string(b)
}
```

</td><td>

```go
func main() {
  body, err := readFile(path)
  if err != nil {
    log.Fatal(err)
  }
  fmt.Println(body)
}

func readFile(path string) (string, error) {
  f, err := os.Open(path)
  if err != nil {
    return "", err
  }

  b, err := io.ReadAll(f)
  if err != nil {
    return "", err
  }

  return string(b), nil
}
```

</td></tr>
</tbody></table>

Uzasadnienie: Programy zawierające wiele funkcji kończących działanie stwarzają kilka problemów:

- Nieczytelny przepływ sterowania: Dowolna funkcja może zakończyć program, co utrudnia analizę przepływu kodu.
- Trudność w testowaniu: Funkcja przerywająca działanie programu przerwie również test, który ją wywołał. Utrudnia to testowanie i stwarza ryzyko pominięcia pozostałych testów w zestawie `go test`.
- Pominięte czyszczenie: Gdy funkcja kończy działanie programu, pomijane są wywołania kolejkowe z instrukcjami `defer`. Zwiększa to ryzyko pominięcia kluczowych zadań sprzątających.

#### Wywołuj exit tylko raz

Jeśli to możliwe, staraj się wywoływać `os.Exit` lub `log.Fatal` **co najwyżej raz** w funkcji `main()`. Jeśli istnieje wiele scenariuszy błędów przerywających wykonanie programu, umieść tę logikę w osobnej funkcji i zwracaj z niej błędy.

Skraca to funkcję `main()` i przenosi kluczową logikę biznesową do osobnej, łatwiej testowalnej funkcji.

<table>
<thead><tr><th>Źle</th><th>Dobrze</th></tr></thead>
<tbody>
<tr><td>

```go
package main

func main() {
  args := os.Args[1:]
  if len(args) != 1 {
    log.Fatal("missing file")
  }
  name := args[0]

  f, err := os.Open(name)
  if err != nil {
    log.Fatal(err)
  }
  defer f.Close()

  // Jeśli wywołamy log.Fatal po tej linii,
  // f.Close() nie zostanie wywołane.

  b, err := io.ReadAll(f)
  if err != nil {
    log.Fatal(err)
  }

  // ...
}
```

</td><td>

```go
package main

func main() {
  if err := run(); err != nil {
    log.Fatal(err)
  }
}

func run() error {
  args := os.Args[1:]
  if len(args) != 1 {
    return errors.New("missing file")
  }
  name := args[0]

  f, err := os.Open(name)
  if err != nil {
    return err
  }
  defer f.Close()

  b, err := io.ReadAll(f)
  if err != nil {
    return err
  }

  // ...
}
```

</td></tr>
</tbody></table>

Powyższy przykład używa `log.Fatal`, ale wytyczna dotyczy również `os.Exit` i dowolnego kodu bibliotecznego wywołującego `os.Exit`.

```go
func main() {
  if err := run(); err != nil {
    fmt.Fprintln(os.Stderr, err)
    os.Exit(1)
  }
}
```

Możesz dostosować sygnaturę funkcji `run()` do własnych potrzeb. Jeśli np. program musi kończyć działanie ze specyficznymi kodami wyjścia dla niepowodzeń, `run()` może zwracać kod wyjścia zamiast błędu. Umożliwia to bezpośrednią weryfikację tego zachowania w testach jednostkowych.

```go
func main() {
  os.Exit(run(args))
}

func run() (exitCode int) {
  // ...
}
```

Mówiąc ogólniej, funkcja `run()` użyta w tych przykładach nie ma charakteru nakazowego. Istnieje elastyczność w kwestii nazwy, sygnatury i konfiguracji funkcji `run()`. Możesz między innymi:

- przyjmować nieprzetworzone argumenty linii poleceń (np. `run(os.Args[1:])`)
- parsować argumenty linii poleceń w `main()` i przekazywać je do `run`
- używać własnego typu błędu do przekazania kodu wyjścia z powrotem do `main()`
- umieścić logikę biznesową w innej warstwie abstrakcji niż `package main`

Wytyczna ta wymaga jedynie, aby w `main()` istniało jedno miejsce odpowiedzialne za faktyczne zamknięcie procesu.

### Unikaj uruchamiania gorutyn bez kontroli ich cyklu życia (fire-and-forget)

Gorutyny są lekkie, ale nie są darmowe: kosztują co najmniej pamięć stosu oraz czas CPU potrzebny na planowanie (scheduling). Choć koszty te są niewielkie przy typowym użyciu, mogą powodować znaczne problemy wydajnościowe w przypadku masowego uruchamiania bez kontrolowanego czasu życia. Gorutyny o niezarządzanym czasie życia mogą również uniemożliwiać odzyskiwanie nieużywanych obiektów przez Garbage Collector i przetrzymywać zasoby.

Dlatego nie dopuszczaj do wycieków gorutyn w kodzie produkcyjnym. Używaj pakietu [go.uber.org/goleak](https://pkg.go.dev/go.uber.org/goleak) do testowania wycieków gorutyn wewnątrz pakietów, które mogą je uruchamiać.

Ogólnie rzecz biorąc, każda gorutyna:

- musi mieć przewidywalny moment, w którym zakończy działanie; lub
- musi istnieć sposób na zasygnalizowanie gorutynie, że powinna się zatrzymać

W obu przypadkach kod wywołujący musi mieć możliwość zablokowania i odczekania na zakończenie gorutyny.

Na przykład:

<table>
<thead><tr><th>Źle</th><th>Dobrze</th></tr></thead>
<tbody>
<tr><td>

```go
go func() {
  for {
    flush()
    time.Sleep(delay)
  }
}()
```

</td><td>

```go
var (
  stop = make(chan struct{}) // nakazuje gorutynie zatrzymanie się
  done = make(chan struct{}) // informuje nas, że gorutyna zakończyła pracę
)
go func() {
  defer close(done)

  ticker := time.NewTicker(delay)
  defer ticker.Stop()
  for {
    select {
    case <-ticker.C:
      flush()
    case <-stop:
      return
    }
  }
}()

// W innym miejscu...
close(stop)  // wyślij sygnał zatrzymania
<-done       // i poczekaj na zakończenie
```

</td></tr>
<tr><td>

Brak możliwości zatrzymania tej gorutyny. Będzie działać do momentu zakończenia aplikacji.

</td><td>

Tę gorutynę można zatrzymać za pomocą `close(stop)` oraz odczekać na jej zakończenie poprzez `<-done`.

</td></tr>
</tbody></table>

#### Czekaj na zakończenie gorutyn

Dla każdej gorutyny uruchomionej przez system musi istnieć sposób na odczekanie na jej zakończenie. Istnieją dwa popularne sposoby:

- Użycie `sync.WaitGroup` do oczekiwania na wiele gorutyn. Stosuj to rozwiązanie, gdy musisz poczekać na zakończenie grupy gorutyn.

  ```go
  var wg sync.WaitGroup
  for i := 0; i < N; i++ {
    wg.Go(...)
  }

  // Oczekiwanie na zakończenie wszystkich:
  wg.Wait()
  ```

- Użycie dodatkowego kanału `chan struct{}`, który gorutyna zamyka po zakończeniu pracy. Stosuj to rozwiązanie, gdy istnieje tylko jedna gorutyna.

  ```go
  done := make(chan struct{})
  go func() {
    defer close(done)
    // ...
  }()

  // Oczekiwanie na zakończenie gorutyny:
  <-done
  ```

#### Unikaj tworzenia gorutyn w `init()`

Funkcje `init()` nie powinny uruchamiać gorutyn. Zobacz również [Unikaj init()](#unikaj-init).

Jeśli pakiet wymaga gorutyny w tle, musi wystawić obiekt odpowiedzialny za zarządzanie czasem życia tej gorutyny. Obiekt ten musi udostępniać metodę (`Close`, `Stop`, `Shutdown` itp.), która zasygnalizuje gorutynie w tle konieczność zatrzymania i poczeka na jej zakończenie.

<table>
<thead><tr><th>Źle</th><th>Dobrze</th></tr></thead>
<tbody>
<tr><td>

```go
func init() {
  go doWork()
}

func doWork() {
  for {
    // ...
  }
}
```

</td><td>

```go
type Worker struct{ /* ... */ }

func NewWorker(...) *Worker {
  w := &Worker{
    stop: make(chan struct{}),
    done: make(chan struct{}),
    // ...
  }
  go w.doWork()
  return w
}

func (w *Worker) doWork() {
  defer close(w.done)
  for {
    // ...
    case <-w.stop:
      return
  }
}

// Shutdown nakazuje pracownikowi zatrzymanie się
// i czeka na zakończenie zadania.
func (w *Worker) Shutdown() {
  close(w.stop)
  <-w.done
}
```

</td></tr>
<tr><td>

Uruchamia gorutynę w tle bezwarunkowo przy zaimportowaniu pakietu. Użytkownik nie ma nad nią kontroli ani możliwości jej zatrzymania.

</td><td>

Uruchamia pracownika tylko wtedy, gdy życzy sobie tego użytkownik. Udostępnia mechanizm wyłączenia, umożliwiając zwolnienie zasobów.

Pamiętaj o użyciu `WaitGroup`, jeśli pracownik zarządza wieloma gorutynami. Zobacz [Czekaj na zakończenie gorutyn](#czekaj-na-zako%C5%84czenie-gorutyn).

</td></tr>

### Preferuj określenie pojemności kontenerów

W miarę możliwości określaj pojemność kontenera, aby z góry przydzielić mu odpowiednią ilość pamięci.
Operacja ta zminimalizuje kolejne alokacje (spowodowane kopiowaniem i zwiększaniem kontenera)
w miarę dodawania nowych elementów.

#### Określaj wskazówki dotyczące pojemności map

Gdy to tylko możliwe, umieszczaj wskazówki (hints)
dotyczące pojemności podczas inicjalizacji mapy za pomocą funkcji `make()`.

```go
make(map[T1]T2, hint)
```

Zapewnienie wskazówki dotyczącej pojemności sprawia,
że funkcja `make()` próbuje dopasować rozmiar mapy w czasie inicjalizacji,
co redukuje czas i alokacje potrzebne na zwiększanie mapy podczas dodawania elementów.

Pamiętaj jednak, że w przeciwieństwie do wycinków (slices),
wskazówki pojemności map nie gwarantują pełnej alokacji z góry,
lecz służą do oszacowania liczby potrzebnych "kubełków" (hashmap buckets).
Alokacje mogą więc nadal występować przy dodawaniu elementów,
nawet przed osiągnięciem określonej pojemności.

<table>
<thead><tr><th>Źle</th><th>Dobrze</th></tr></thead>
<tbody>
<tr><td>

```go
files, _ := os.ReadDir("./files")

m := make(map[string]os.DirEntry)
for _, f := range files {
    m[f.Name()] = f
}
```

</td><td>

```go

files, _ := os.ReadDir("./files")

m := make(map[string]os.DirEntry, len(files))
for _, f := range files {
    m[f.Name()] = f
}
```

</td></tr>
<tr><td>

Mapa `m` stworzona bez wskazówki rozmiaru; mapa będzie dynamicznie zmieniać rozmiar, powodując wielokrotne alokacje.

</td><td>

Mapa `m` stworzona ze wskazówką rozmiaru; wystąpi mniej alokacji w czasie przypisywania elementów.

</td></tr>
</tbody></table>

#### Określaj pojemność wycinków

Tam, gdzie to możliwe, podawaj wskazówki dotyczące pojemności podczas inicjowania wycinków za pomocą funkcji `make()`, szczególnie przy operacjach dodawania elementów (`append`).

```go
make([]T, length, capacity)
```

Inaczej niż w przypadku map, pojemność wycinków nie stanowi jedynie wskazówki: kompilator przydzieli dokładnie tyle pamięci, ile dostarczono w argumencie `capacity`, co oznacza, że kolejne operacje `append()` nie będą pociągały za sobą alokacji pamięci (do momentu, gdy długość wycinka zrówna się z jego pojemnością – po tym czasie każde kolejne dodanie elementu będzie wymagało zmiany rozmiaru w celu pomieszczenia dodatkowych elementów).

<table>
<thead><tr><th>Źle</th><th>Dobrze</th></tr></thead>
<tbody>
<tr><td>

```go
for n := 0; n < b.N; n++ {
  data := make([]int, 0)
  for k := 0; k < size; k++{
    data = append(data, k)
  }
}
```

</td><td>

```go
for n := 0; n < b.N; n++ {
  data := make([]int, 0, size)
  for k := 0; k < size; k++{
    data = append(data, k)
  }
}
```

</td></tr>
<tr><td>

```plain

```

</td><td>

```plain
BenchmarkGood-4   100000000    0.21s
```

</td></tr>
</tbody></table>

## Styl

### Unikaj zbyt długich linii

Unikaj wierszy kodu, które wymagają od czytelnika przewijania w poziomie lub znacznego obracania głowy.

Zalecamy mięki limit długości linii wynoszący **99 znaków**. Autorzy powinni dążyć do zawijania wierszy przed osiągnięciem tego limitu, jednak nie jest to sztywna bariera. Kod może przekraczać ten limit w uzasadnionych przypadkach.

### Spójność ponad wszystko

Niektóre wytyczne przedstawione w tym dokumencie można ocenić obiektywnie,
inne są sytuacyjne, kontekstowe lub subiektywne.

Ponad wszystko inne: **zachowaj spójność**.

Spójny kod łatwiej się utrzymuje, łatwiej analizuje,
wymaga mniejszego nakładu poznawczego i ułatwia migrację
oraz aktualizację wraz z pojawianiem się nowych konwencji lub naprawianiem błędów.

Z drugiej strony baza kodu zawierająca wiele różnych,
sprzecznych stylów powoduje narzut utrzymaniowy,
niepewność i dysonans poznawczy, co przekłada się bezpośrednio na spadek prędkości pracy zespołu,
uciążliwe przeglądy kodu (code review) i powstawanie błędów.

Podczas stosowania tych wytycznych zaleca się wprowadzanie zmian na poziomie całego pakietu (lub większym) –
stosowanie ich na poziomie pojedynczego podpakietu wprowadza mieszankę stylów w tej samej bazie kodu.

### Nazwy pakietów

Podczas nazywania pakietów wybieraj nazwy, które:

- Składają się wyłącznie z małych liter. Bez wielkich liter i podkreśleń.
- Nie wymagają zmiany nazwy poprzez aliasy ("named imports") w większości miejsc wywołania.
- Są krótkie i zwięzłe. Pamiętaj, że nazwa jest używana w pełnej postaci w każdym miejscu wywołania.
- Nie występują w liczbie mnogiej. Na przykład `net/url`, a nie `net/urls`.
- Nie nazywają się "common", "util", "shared" ani "lib". Są to złe, nieinformacyjne nazwy.

Zobacz również [Package Names](https://go.dev/blog/package-names) oraz [Style guideline for Go packages](https://rakyll.org/style-packages/).

### Nazwy funkcji

Przestrzegamy konwencji społeczności Go używającej konwencji [MixedCaps dla nazw funkcji](https://go.dev/doc/effective_go#mixed-caps). Wyjątkiem są funkcje testowe, które mogą zawierać znak podkreślenia w celu grupowania powiązanych przypadków testowych, np. `TestMyFunction_WhatIsBeingTested`.

### Aliasy importowanych bibliotek

```go
  client "example.com/client-go"
  trace "example.com/trace/v2"

```

### Grupowanie i porządkowanie funkcji

- Funkcje powinny być sortowane w przybliżonej kolejności wykonywania (call order).
- Funkcje wewnątrz tego samego pliku powinny być grupowane według odbiorcy (receiver).

Dlatego najpierw w pliku powinny pojawić się funkcje eksportowane, zaraz po definicjach `struct`, `const`, `var`.

Funkcja `newXYZ()`/`NewXYZ()` może pojawić się po definicji typu, ale przed pozostałymi metodami tego odbiornika.

Z racji tego, że funkcje są grupowane według odbiorcy, ogólne funkcje narzędziowe powinny znajdować się pod koniec pliku.

```go
func calcCost(n []int) int {...}

func (s *something) Stop() {...}

func newSomething() *something {
    return &something{}
}
```

</td><td>

```go
type something struct{ ... }

func newSomething() *something {
    return &something{}

func (s *something) Cost() {

func (s *something) Stop() {...}

func calcCost(n []int) int {...}
```

</tbody></table>

### Zagnieżdżanie w strukturach (embedding)

Typy osadzone powinny znajdować się na samej górze listy pól struktury i być oddzielone pustą linią od pól zwykłych.

<table>
<thead><tr><th>Źle</th><th>Dobrze</th></tr></thead>
<tbody>
<tr><td>

```go

  version int
  http.Client
```

</td><td>

```go
}
```

</td></tr>
</tbody></table>

Osadzanie powinno przynosić wymierne korzyści, takie jak dodawanie lub rozszerzanie funkcjonalności w sposób semantycznie poprawny. Powinno to odbywać się bez negatywnych skutków ubocznych dla użytkownika (zobacz też: [Unikaj osadzania typów w strukturach publicznych](#unikaj-osadzania-typ%C3%B3w-type-embedding-w-strukturach-publicznych)).

Wyjątek: Mutexy nie powinny być osadzane, nawet w typach nieeksportowanych. Zobacz też: [Poprawność wartości zerowych Mutexów](#poprawno%C5%9B%C4%87-warto%C5%9Bci-zerowych-mutex%C3%B3w).

Zagnieżdżanie **nie powinno**:

- Być zabiegiem czysto kosmetycznym lub motywowanym jedynie wygodą.
- Utrudniać konstruowania lub użytkowania typu zewnętrznego.
- Wpływać na wartość zerową typu zewnętrznego. Jeśli typ zewnętrzny ma użyteczną wartość zerową, osadzenie typu wewnętrznego nie powinno tego zmieniać.
- Upubliczniać w efekcie ubocznym niepowiązanych funkcji lub pól.
- Eksponować typów nieeksportowanych.
- Wpływać na semantykę kopiowania typu zewnętrznego.
- Zmieniać API lub semantyki typu zewnętrznego.
- Osadzać niekanonicznej formy typu wewnętrznego.
- Upubliczniać szczegółów implementacyjnych.
- Pozwalać użytkownikowi na obserwowanie lub kontrolę elementów wewnętrznych.
- Zmieniać ogólnego zachowania funkcji wewnętrznych poprzez zawijanie (wrapping) w sposób, którego użytkownicy się nie spodziewają.

Mówiąc krótko: osadzaj świadomie i z celowością. Dobrym testem jest pytanie: "Czy wszystkie te wyeksportowane wewnętrzne metody/pola dodałbym bezpośrednio do typu zewnętrznego?". Jeśli odpowiedź brzmi "niektóre" lub "nie", nie osadzaj typu – użyj zwykłego pola.

<table>
<thead><tr><th>Źle</th><th>Dobrze</th></tr></thead>
<tbody>
<tr><td>

```go

    // Źle: A.Lock() oraz A.Unlock() są teraz
    //      dostępne, nie dają korzyści
    //      i pozwalają użytkownikom kontrolować
    //      szczegóły wewnętrzne struktury A.
    sync.Mutex

```

</td><td>


</td></tr>
<tr><td>

```go

    // Źle: wskaźnik zmienia użyteczność wartości zerowej

    // inne pola
```

</td></tr>
<tr><td>

```go

```

</td><td>


### Nazewnictwo funkcji "Printf-style"

## Wzorce (Patterns)

### Tablice testowe

Stosuj testy oparte o tablice testowe z wykorzystaniem [podtestów (subtests)](https://go.dev/blog/subtests) w celu uniknięcia powielania kodu, gdy główna logika testów jest powtarzalna.

Jeśli testowany system musi zostać przetestowany pod kątem *wielu warunków*, w których zmieniają się określone dane wejściowe i wyjściowe, należy użyć testu opartego na tablicy testowej, aby zredukować duplikację i poprawić czytelność.

Tablice testowe ułatwiają dodawanie kontekstu do komunikatów błędów, redukują duplikacje w logice oraz ułatwiają dodawanie nowych scenariuszy testowych.

Postępujemy zgodnie z konwencją mówiącą, że wycinek struktur testowych nazywamy `tests`, a każdy przypadek testowy `tt`. Ponadto zachęcamy do jawnego oznaczania danych wejściowych i wyjściowych prefiksami `give` oraz `want`.

```go

  give     string
  wantHost string
  wantPort string
}{
  // ...
}

for _, tt := range tests {
  // ...
}
```

#### Unikaj niepotrzebnej złożoności w tablicach testowych

Tablice testowe mogą stać się trudne do odczytania i utrzymania, jeśli podtesty zawierają warunkowe asercje lub inną logikę rozgałęziającą. Tablic testowych **NIE należy** stosować, gdy wewnątrz podtestów wymagana jest złożona logika warunkowa (tzn. złożona logika wewnątrz pętli `for`).

Duże, złożone tablice testowe obniżają czytelność i utrzymywalność, ponieważ debugowanie niepowodzeń testów staje się utrudnione.

Tego typu tablice testowe powinny zostać podzielone na wiele osobnych tablic testowych lub osobne funkcje testowe `Test...`.

Idee, do których należy dążyć:

* Skupiaj się na jak najwęższej jednostce zachowania.
* Minimalizuj "głębokość testu" (test depth) i unikaj warunkowych asercji (patrz niżej).
* Upewnij się, że wszystkie pola tablicy są używane we wszystkich testach.
* Upewnij się, że cała logika testu uruchamia się dla wszystkich przypadków w tablicy.

W tym kontekście "głębokość testu" oznacza liczbę kolejnych asercji w danym teście, które wymagają spełnienia poprzednich asercji (podobny pomysł do złożoności cyklomatycznej). Płytsze testy oznaczają mniej zależności między asercjami i przede wszystkim mniejsze prawdopodobieństwo, że asercje będą warunkowe.

W praktyce tablice testowe stają się skomplikowane, gdy korzystają z wielu ścieżek rozgałęzień (np. `shouldError`, `expectCall`), zawierają liczne instrukcje `if` dla konkretnych oczekiwań atrap (mocków) (np. `shouldCallFoo`) lub przechowują funkcje wewnątrz tablicy (np. `setupMocks func(*FooMock)`).

Jednak przy testowaniu zachowania, które zmienia się wyłącznie na podstawie zmienionych danych wejściowych, preferowane może być pogrupowanie podobnych przypadków w tablicy testowej, aby lepiej zilustrować zmianę zachowania, zamiast rozbijania porównywalnych przypadków na osobne testy.

Jeśli ciało testu jest krótkie i proste, dopuszczalne jest posiadanie pojedynczej ścieżki rozgałęzienia dla przypadków sukcesu i błędu z polem tablicy takim jak `shouldErr` do określenia oczekiwań dotyczących błędów.

<tbody>
<tr><td>

```go
      }

func TestShouldCallYAndFail(t *testing.T) {
  // konfiguracja mocków
  ctrl := gomock.NewController(t)
  xMock := xmock.NewMockX(ctrl)

  yMock := ymock.NewMockY(ctrl)
  yMock.EXPECT().Call().Return("YResponse", nil)

  _, err := DoComplexThing("inputY", xMock, yMock)
  assert.EqualError(t, err, "Y failed")
}
```

Złożoność utrudnia modyfikację, zrozumienie oraz udowodnienie poprawności testu.

Choć nie ma tu sztywnych reguł, czytelność i łatwość utrzymania powinny zawsze być priorytetem przy wyborze między tablicą testową a osobnymi testami.

#### Testy współbieżne (Parallel Tests)

Testy współbieżne (podobnie jak niektóre pętle uruchamiające gorutyny lub przechwytujące referencje) muszą dbać o jawne przypisywanie zmiennych pętli wewnątrz jej zasięgu, aby upewnić się, że przechowują one oczekiwane wartości.

```go
tests := []struct{
  give string
  // ...
}{
  // ...
}

for _, tt := range tests {
  t.Run(tt.give, func(t *testing.T) {
    t.Parallel()
    // ...
  })
}
```

W powyższym przykładzie musimy zadeklarować zmienną `tt` w zasięgu iteracji pętli z powodu użycia `t.Parallel()`. W przeciwnym razie większość lub wszystkie testy otrzymają nieoczekiwaną wartość `tt` lub wartość zmieniającą się w trakcie ich wykonywania.

### Opcje funkcjonalne

Opcje funkcjonalne to wzorzec, w którym deklarujesz nieprzezroczysty typ `Option`, rejestrujący informacje w pewnej wewnętrznej strukturze. Przyjmujesz zmienną liczbę takich opcji i działasz na podstawie pełnej informacji zapisanej przez nie w tej wewnętrznej strukturze.

Używaj tego wzorca dla opcjonalnych argumentów w konstruktorach i innych publicznych interfejsach API, w przypadku których przewidujesz potrzebę ich późniejszego rozszerzania – zwłaszcza jeśli funkcja przyjmuje już trzy lub więcej argumentów.

Sugerowany sposób implementacji tego wzorca opiera się na interfejsie `Option` z nieeksportowaną metodą rejestrującą opcje w nieeksportowanej strukturze `options`.

```go
type options struct {
  cache  bool
  logger *zap.Logger
}

type Option interface {
  apply(*options)
}

type cacheOption bool

func (c cacheOption) apply(opts *options) {
  opts.cache = bool(c)
}

func WithCache(c bool) Option {
  return cacheOption(c)
}

type loggerOption struct {
  Log *zap.Logger
}

func (l loggerOption) apply(opts *options) {
  opts.logger = l.Log
}

func WithLogger(log *zap.Logger) Option {
  return loggerOption{Log: log}
}

// Open tworzy połączenie.
func Open(
  addr string,
  opts ...Option,
) (*Connection, error) {
  options := options{
    cache:  defaultCache,
    logger: zap.NewNop(),
  }

  for _, o := range opts {
    o.apply(&options)
  }

  // ...
}
```

Istnieje sposób implementacji tego wzorca oparty na domknięciach (closures), jednak uważamy, że powyższa wersja zapewnia autorowi większą elastyczność i jest łatwiejsza w debugowaniu i testowaniu. Umożliwia w szczególności porównywanie opcji między sobą w testach oraz atrapach (mockach), co przy domknięciach jest niemożliwe. Pozwala też opcjom implementować inne interfejsy, takie jak `fmt.Stringer`.

## Lintowanie

Ważniejsza od jakichkolwiek "błogosławionych" zestawów linterów jest konsekwencja w lintowaniu całej bazy kodu.

Zalecamy stosowanie przynajmniej wymienionych linterów, ponieważ uważamy, że pomogą one wyłapać najczęstsze błędy oraz ustanowią wysoki próg jakościowy bez zbędnego narzucania reguł:

- [errcheck](https://github.com/kisielk/errcheck) do upewnienia się, że błędy są obsługiwane
- [goimports](https://pkg.go.dev/golang.org/x/tools/cmd/goimports) do formatowania kodu i zarządzania importami
- [revive](https://github.com/mgechev/revive) do wskazywania typowych błędów stylistycznych
- [govet](https://pkg.go.dev/cmd/vet) do analizy kodu pod kątem typowych błędów
- [staticcheck](https://staticcheck.dev) do różnorodnych analiz statycznych

  > **Uwaga**: [revive](https://github.com/mgechev/revive) jest nowoczesnym, szybszym następcą przestarzałego narzędzia [golint](https://github.com/golang/lint).

### Runnery linterów

Zalecamy stosowanie [golangci-lint](https://github.com/golangci/golangci-lint) jako głównego runnera do lintowania kodu w języku Go, przede wszystkim z powodu jego wydajności w dużych bazach kodu oraz możliwości konfiguracji i używania wielu standardowych linterów jednocześnie. Repozytorium to posiada przykład pliku konfiguracyjnego [.golangci.yml](https://github.com/uber-go/guide/blob/master/.golangci.yml) zawierającego rekomendowane lintery oraz ustawienia.

golangci-lint udostępnia [wiele linterów](https://golangci-lint.run/usage/linters/). Wyżej wymienione lintery są rekomendowane jako zestaw podstawowy, jednak zachęcamy zespoły do dodawania dodatkowych linterów mających sens w kontekście ich projektów.
